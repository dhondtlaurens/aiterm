# Holistic code review and refactor

Status: approved for implementation by Laurens on 2026-10-29 ("implement now"). Preserve the current successful Operator behavior and leave the running app/daemon untouched.

## Goal

Make AiTerm simpler to understand, change and run across the complete repository. Reduce the Operator's conceptual and implementation complexity, consolidate genuinely reusable operations, apply sound Swift and Python practices, improve measured performance, and replace accumulated test and documentation history with a coherent account of the product that remains.

Laurens explicitly allows simplifying Operator features and workflow where justified, with a subsequent overriding constraint: the current Operator run is working as intended and must not regress. Treat broadcast history as nonexistent for schema/compatibility design, while preserving the current successful workflow. This does not authorise deleting real projects, worktrees, conversations, credentials or other user files, or interfering with the currently running app/daemon.

## Approach

Audit by user journey and state ownership, then deliver small working slices. Decide the Operator's product model before refactoring its machinery; extracting more helper files around the existing complexity is insufficient. Preserve the useful foundations already present: native macOS UI, Core/UI/app dependency direction, daemon ownership of iTerm2, explicit I/O seams, atomic persistence, bounded process execution, and observation scoped to what a row draws.

Prefer ordinary concrete types, explicit ownership and a few cohesive services. Use protocols at real I/O or variability boundaries, value types for facts and decisions, exhaustive enums for finite alternatives, and actor isolation for mutable asynchronous ownership. Do not introduce a general reducer framework, event store, plugin architecture, protocol per class, speculative caching or mandatory file-size/line-count targets. Moving blocking work into an actor does not make it nonblocking.

The prior reviews under `docs/superpowers/` are evidence to recheck, not requirements to inherit. In particular, their compatibility, unchanged-pixel and feature-preservation restrictions do not govern this work. Their resolved findings are not new discoveries.

## Product decisions

### Confirmed

- The whole repository is in scope, including scripts, hook integrations, fixtures, test infrastructure, release/update paths and documentation.
- Operator feature simplification is permitted; core work remains plan, launch workers, monitor, review and finish.
- No legacy broadcast readers, migrations, old prompt variants or round-trip preservation machinery solely for historical broadcasts.
- The supported current broadcast format is the structured format written at `f152f6e9`. Keep its known run/task/settings/review/goal/extra-tab fields readable while refactoring; this is the current contract, not a request for older-format compatibility or unknown-field preservation. Test restart/reconnect from a synthetic current-format save. Do not silently turn a supported run into `unreadableRuns` or drop a task's `operated` link.
- Current Git/worktree safety, user pause/stop/takeover intent, correct commit/repository targeting, and uncertain delivery/launch outcomes remain real requirements. These are normal failure modes, not ultra edge cases.
- Existing non-Operator features remain unless the audit establishes dead code or a separate concrete simplification is selected.
- No live accounts, personal preferences or running sessions are mutated by the audit or benchmarks. Use isolated repositories, scratch homes, fake hosts and hidden windows.

### Preserve the current successful Operator workflow

A read-only inspection of the current saved configuration found an active run with structured task settings, a goal, the Oracle enabled, all Jira/Review/Merge slices enabled, six extra worker tabs, and tasks in working, accepted and published states targeting merge. Those facts establish that extra worker tabs and the goal workflow are in use. They are not speculative flexibility to discard.

Preserve multiple worker tabs per task, review/fix rounds, optional goals and additional rounds, backlog/Oracle policy, all current tool capabilities, task outcomes, Jira integration, human review, pause/resume, takeover, questions, activity, summary, model selection and order/code dependencies. Simplify the implementation first. Keep the generated brief, tool names/arguments/descriptions and model-visible status/refusal semantics for current-format runs stable during structural changes. The shell gate is reviewed as a policy adapter, not expanded into a comprehensive shell interpreter.

Prompt/status-language improvements are a separate, conditional slice after the structural refactor. They may reduce repetition and contradictory guidance only after current-setup real-agent evals pass against a captured pre-change baseline. If that empirical proof cannot run, keep current wording and report the limitation; do not ship a prompt rewrite labelled behavior-preserving on deterministic tests alone. A resumed Operator rewrites its brief with `--system-prompt-snapshot off`, so the contract matters on resume as well as fresh launch.

Initial suggestions to remove extra workers and goal-expansion rules were withdrawn after checking this evidence. They are not options awaiting an implicit yes. Any later recommendation to change these behaviors must name its benefit, the exact lost capability and current-run impact, and receive a separate explicit decision.

No visual redesign is currently required for the refactor. Preserve the working setup and board. If the audit identifies a useful visual/workflow change, first draw the options in the design-system Proposals tab, publish them using Claude if needed, and wait for the user's selection before writing the affected Swift. Do not produce a speculative redesign merely to justify a refactor.

## Target ownership

| Area | One owner of decisions | Effects and presentation |
| --- | --- | --- |
| Persisted workspace and current run facts | `WorkspaceStore`, using current Codable domain models | Save/flush reports success or failure; a successful durable boundary precedes irreversible follow-up work. |
| Operator plan and task transitions | Pure rules in `AiTermCore/Operators` | Tool and UI adapters call the same commands. Store durable facts; derive readiness, attention and display labels. |
| Operator runtime | A smaller `OperatorController`, with explicit owned jobs | Starts/stops jobs, applies their results only while their identities still match, and coordinates scheduling/completion. |
| Checkout, agent launch, window adoption and task cleanup | Shared concrete task operations used by manual and Operator callers | Caller supplies policy such as background focus or worker brief. iTerm2 effects remain daemon-owned. |
| Worker observations | One coherent read of worker/session/transcript facts per observation pass | Liveness, ended-turn and branch rules consume the same observations. No duplicate persisted truth. |
| Publication and external integration | Task finishing service plus host/Jira adapters | Explicit operation identity, accepted commit and repository; recover uncertain writes by reading the actual result. |
| UI | Small feature view models and value projections | `AppController` composes owners. Views read focused state, use AiTermUI primitives, and avoid I/O in `body`. |
| Daemon | `Service` composes registry/status, delivery, windows, hooks and RPC adapters | asyncio loop stays responsive; blocking filesystem work remains off-loop with bounded ownership. |

An effect can finish after an `await`, cancellation, pause or removal. Put identity/revision validation at the effect owner and before consequential writes, rather than repeating loosely different predicates throughout callers. Do not erase guards until the replacement covers the same plausible failure.

## Complete-review ledger

During implementation, enumerate tracked source, tests, scripts, hooks and documentation. Record every file as reviewed with a decision: keep (reason), simplify, consolidate, delete, or investigate. This is a review record in this plan, not a source-scanning test. Group routine keep decisions by cohesive area while recording concrete changes and exclusions by path. ### Runtime and performance evidence

Before product edits, record the full-suite baseline and repeatable in-process workloads: empty idle owners and fake daemon; a warmed workspace with 2 projects, 6 tasks and their sessions; an active synthetic broadcast with extra tabs/goals/worker updates; a larger 50-task workspace; and a growing transcript with a long-running tool. Use scratch data and fake iTerm/hosts. Measure relevant wall time distributions, process counts, host requests, filesystem reads/bytes, state-write counts, row invalidations and shutdown cleanup. Distinguish cold from warm behavior and fixture costs from real app/live service latency.

Use `OperatorWorld`/`OperatorServiceFixtures`, daemon pytest with fake iTerm, `GitSpawnCountTests` and row-redraw fixtures as the supported measurement seams. Profile the isolated fixture/test host if CPU or redraw claims need Instruments; measure asyncio-loop responsiveness against the fake daemon. Add assertions only for important work bounds, not incidental exact internal call sequences. Report baseline, final numbers, workload, method and limitations; no invented percentage target or unmeasured whole-app speedup. A cache earns its invalidation policy with a measured repeated cost.

Do not use `scripts/run-dev.sh`, launch/install a normal second AiTerm, replace the app, or restart/adopt its real daemon. The current app has a fixed support directory, socket and hook port; changing only a home path would not isolate it. Bundle verification is static, not live proof. Use fixture-backed test renderers for UI proof. Before running standalone snapshot scripts, verify their startup path has no live-state/settings effects: `AiTermApp.main` currently calls support-directory migration and constructs a live controller before the snapshot-mode check. Defer those script checks if isolation cannot be established; do not treat their early snapshot exit as proof by itself. A real installed-app/iTerm smoke check is deferred until the active run has ended and the user chooses the switchover; report that limit. Do not add new sandbox/launch plumbing solely to manufacture a performance claim.

In particular, verify bounded/deduplicated observation work, responsive UI during filesystem/process work, no serial host re-fetch per status consumer, coalesced durable writes, and no orphan task/process/window after normal stop, disconnect or cancellation. Do not add an entire generic scheduler to solve a single observed bottleneck.
