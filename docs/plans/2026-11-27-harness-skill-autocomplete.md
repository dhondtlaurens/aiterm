# Antigravity and Pi skill autocomplete

## Goal

AiTerm's first-prompt editor should offer installed Antigravity plugin skills and Pi package skills. In the reported setup both terminal menus offer eleven skills from one pack. AiTerm offers zero on these two harnesses and all eleven on Claude Code and Codex. Typing a leaf prefix such as `/deb` and pressing Return should insert Antigravity's `/<plugin>:debug` or Pi's `/skill:debug`.

## Approach

**Antigravity.** Run `agy plugin list --json` once per catalogue load for the user's home. For each enabled plugin, qualify each advertised skill name with its plugin name exactly once. The installed CLI's interactive menu shows the built-in `/plan` and the plugin's `/<plugin>:plan` as separate rows. The ACP list reports both as `plan`. The interactive menu is the reference for the invocation AiTerm inserts. Use the plugin as the source label and read descriptions from the reported plugin path where available. The CLI list controls membership even when a description is missing. Merge the result with each project's existing filesystem completions. The Signal sheet reuses one plugin read across all its projects.

**Pi.** Send one correlated `get_commands` request to offline RPC with extensions and MCP disabled and session persistence off. Use the selected project as the working directory. Task and review creation always have a project. The existing home-only consumers cover full-support agents, so they never need a Pi subprocess. Use the returned skill entries' names, descriptions and source metadata. Pi resolves packages and chooses which resources to load under its project trust rules. Keep existing prompt templates. Treat the skill list as authoritative, including an empty list. On first visit, RPC under the default ask policy exposes user packages only when the project requires trust and has no stored decision. Offer those user skills. A grant for that same directory or an ancestor applies at the next load. A grant for a child worktree never grants trust to the repository root or a sibling. Pre-creation follows the worktree rules below.

Respect Pi's interactive `enableSkillCommands` preference for both the RPC and filesystem paths. RPC includes skill entries even when interactive suggestions are disabled. Use the same agent directory as the child CLI (including its configured directory override). Read its global settings.json and the project's .pi/settings.json. Within each file prefer the top-level boolean over the legacy skills.enableSkillCommands field. The default is true. For a project override, the presence of .pi/settings.json itself triggers Pi's trust check. Use the nearest boolean decision for the canonical project path or an ancestor in the agent directory's trust.json. Absent a decision, only a global defaultProjectTrust of always admits that override in offline RPC. A trusted project override takes precedence over the global setting. Never pass a trust override to Pi or write a trust decision. On native probe failure, return eligible filesystem skills, omitting project skills where trust is denied or still pending. Preserve ordinary prompt-template behavior. Use synthetic accepted, denied and undecided inputs to contract-test these rules against Pi's interactive behavior.

**Loading and refresh.** Keep the existing file-stamp cache for filesystem reads. Fetch native results outside that cache on every catalogue load and keep them for filtering within that load. Make model readiness independent of skill discovery. Clear the previous selection's suggestions when switching harnesses and publish asynchronous results only for the current load. Run probes off the main thread with a deadline, close stdin, and use the filesystem fallback on launch, timeout, truncation or parse failure. Retry on the next load.

**Isolation.** Inject the native reader at the live application boundary. Give direct catalogue calls, scratch controllers and snapshots a filesystem-only default. Share the reader through the existing task, review, Settings and Signal composition paths, respecting each screen's existing set of harnesses.

## Worktree behavior

Pi records trust for the directory in which the person grants it, or for a parent they choose. Task creation currently loads suggestions from the repository before the new task worktree exists. A grant saved in an existing worktree does not reach this repository-level probe. Test a decision in one task worktree, a sibling task, and a grant on the common worktree parent.

Use an existing destination worktree for discovery when its path is known. For a prospective worktree, keep the existing loose project skill suggestions while trust is undecided, subject to the effective skill-command preference. These are suggestions for the first prompt, which Pi can use if the person trusts the new folder. Show installed package skills reported by the native lookup. Honor an explicit denial for the destination and never transfer a sibling's grant. This refines the empty-reply and fallback rules above for a worktree that has yet to be created.
