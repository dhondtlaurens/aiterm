# Refactor round two: evidence

The [plan](../plans/2026-11-10-obsessive-refactor.md) has ten phases. This record holds what each
one measured and proved, in phase order (the phases merged in another order), and ends with the
close-out: every budget, defect, drop and decision in one place.

## The audit behind the plan

Nine reviewers each read one lane completely on 2026-11-10, read-only: Operator runtime, Operator
tool handlers, Core Operator rules, app shell, views, Core infrastructure, integrations, daemon,
tests and scripts. Six of their claims were re-checked against the source by the planner and held.
Their findings, with file and line evidence, are the plan's phases. Codex challenged the plan in two
rounds; the second found nothing. The audit ran no build and no test: every number below was
measured afterwards.

in the test with it, and none may raise it. Swift counts come from `WorkMeter`, a task-local a test
binds, so suites running side by side count only their own work and the app counts nothing. Daemon
counts come from a counted `registry.all` and a Python audit hook that sees the worker threads.

What the numbers change in the plan's priorities:

- **Status building is cheaper than the audit read it.** One build per session event, two per tick,
  three per mutating call, about a millisecond each at 20 tasks. Sharing one snapshot per pass
  (phases 4 and 5) can take a tick from 2 to 1 and a call from 3 to at most 2: worth doing with the
  restructure, not on its own.
- **Unchanged turns are read again on every event.** Nine reads asked for per session event and per
  tick in a broadcast of ten tabs, each a transcript tail read off the main actor. This is the
  largest repeated work found and the first thing phase 5 should lower.
- **Host lookup by git process is per host call, not per pass:** 40 processes for one cold
  `run_status` over 20 tasks (phase 6), and one per task per minute while reviews are watched
  (phase 5).
- **`worktree list` runs five times per Shelve and three per restore** (phases 2 and 7), and the
  branch watch repeats seven git lookups per pass for a message that has not changed (phase 5).
- **The sidebar derives the requests three times per refresh**, four with the board open (phase 4).
- **A synchronous save of a 312 KB workspace takes about 7 ms in a debug build.** That is under half
  a frame, on the main actor, at each of the 44 flush sites. It is the input for the plan's
  measure-then-decide item, not a decision: the cloned backup in phase 2 removes one of the two
  writes either way.

`Budget.settle` waits on the owners' `last…` task handles. Phase 5 replaces those handles with one
settle seam, and moves this helper to it.

A steady tick opens no transcript: the cost of re-reading a whole transcript after a restore, and
of reading a Codex rollout twice, shows only on a first read or a change, which phase 1 measures
with tests of its own.

Dropped: background transcript starting offset and marker prefilter. There is no byte checkpoint
at work start in today's `Turn`, only a wall-clock cutoff. Existing coverage writes qualifying
launch records before SessionStart is applied; taking the file's current size there discards those
jobs. An absent marker also cannot prove valid JSON: the malformed-history recovery test requires
that line to establish a gap. Preserving those results leaves the restore budget unchanged:
`test_restore_background_transcript_read_budget` parses 1,002 lines and reads one complete file
before and after. No offset or prefilter code is retained. Existing tests are not deleted.

Cursor cache: the fast-hit stamp includes device, inode, target mtime/ctime and size. Offset
reset uses `JsonlCursor.rewritten` (inode change or shrink) plus changed metadata at the same
completed size; it does not compare the old device independently when a file grows. The opened
file's inode/device are checked against the stat for this read, which is a different check.
An in-place rewrite that grows, or a cross-device replacement with a colliding inode that grows,
can therefore retain the prefix until replacement with a different inode, shrink, pruning or
restart. There is no timed revalidation; the producer's append-only contract bounds that reuse.
I/O failures do not commit a new cursor. A short read keeps only actual-byte progress and the
last complete facts, as main did, and never memoizes the full-file stamp; the next call resumes
without requiring a file change. A decoder exception makes only its affected field unavailable
on the first reading, and is reported once. As on main, complete-byte traversal is retained with
only the facts parsed before that field's failing record; unchanged later readings return those
facts without I/O or another error log. Parsing that field resumes with newly appended bytes.
Round 1 incorrectly retried the failed batch every tick; round 2 corrects that behavior. Review
M2 explicitly retains the more-correct
same-size rewrite handling and its costs, detailed below.
Subagent memo: each read first checks the directly named file and then stats the remembered real
target; a disappeared target is searched again, and an unreadable target retried, and inactive paths are pruned. A second
competing nested file cannot replace a still-present memoized target until pruning or restart;
there is no timed rediscovery. Agent transcript names identify one child; tests cover removal and
retry. The tail-content stamp also includes the real target's inode and ctime.

### 1c: test activity

Service accepts an injected reader whose directory the test fixture sets before construction;
the real-entry composition also needs the seam (missed here, corrected in review round 1, I1).
Valid records are cached by the opened target's
(device, inode, ctime, mtime, size), and the stamp must remain unchanged during the read to cache
it. Invalid, failed and changing reads are not cached; missing records are pruned. Same-size,
same-date rewrites, symlink retargeting and a transient permission failure without a stamp change
have explicit tests. The cache cannot see a filesystem that lies about all five stamp fields;
normal local filesystem changes update inode or ctime, including restored mtime. There is no
periodic content revalidation beyond that filesystem contract.

### 1f: task index, intentional missing resources and housekeeping

by ordered insertion. They resolve current SessionInfo values rather than retain replaced objects.

out-of-band mutation of a snapshot's ownership/position fields until the next snapshot; those
fields have one production writer, the registry's snapshot application. No TTL or failed read is
stored by the index.

`SessionNotFound(KeyError)` marks intentional absence in the port/adapter and delivery. RPC and
delivery guards catch only that type; KeyError's identifier formatting, and therefore existing
missing-resource reply wording, is preserved. FakeIterm raises the same intentional absence at

payload KeyError propagates. Optional HookEvent fields are keyword-only after cwd; parser and
test call sites name them. `tests/builders.py` now owns session files, raw sessions, parent/child

`test_a_conversation_already_indexed_is_placed_without_a_scan`, with the same no-scan assertion.

Ruff enables BLE and RUF100. Logging already satisfies BLE at many catch boundaries, so unused

### What differs from main, explicitly retained or approved

**M2, retained by review:** Main's inode/size cursors left same-size rewrites and truncation
regrown to the old size stale. The new complete-size stamp re-reads them. A permission/attribute
change that changes ctime at that same size also forces that read even when content is unchanged.
For a large version/boundary pair main did 0 opens/0 bytes on such a metadata-only change; the
new cursor does 1 open and the 8 MiB tail, or the whole file once if the head is needed. These are
the same 8,388,608-byte / 8,806,591-byte shapes measured by the first-sight budgets. Context's
ctime-aware stamp can also add its existing reverse-token-count read, one open, on that change.

### What changed, by to-do

- **2b. Lanes.** `GitLanes` keeps one serial queue per repository, keyed by its git common directory
  read from disk, so finding a lane spawns no process; a project's folder and its worktrees share
  one. Creation, removal, restore, pull, rebase, the project-folder switch, Fix landing, local merge,
  the merged-branch check and a worker checkout run on their repository's lane. A head, the unsaved
  work check and Remove's unlisted-folder question run on the shared pool. Proved by the rendezvous
  test (`GitLanesTests`): a job on one repository's lane waits for a job on another's to start.
- **2c. Bounded output.** `ProcessRunner.run` takes a limit on standard output and reports
  truncation; `GitRunning.output` is git's output as printed, bounded and untrimmed, and `run` trims
  above it. The Operator's diff readers read at most 8 MiB of a task's or a closed task's patch and
  1 MiB of the uncommitted one, trimmed as before: replies are byte for byte today's below the bound.
  A patch cut at the bound marks the file it stops in, and the reply, `truncated`.
  The two `git status --porcelain` reads under "Left out" keep `run`'s trimmed text.
- **2d. Typed home.** `Repository.head(at:)` and `isClean(at:untracked:)`; `CommitId` (40 or 64 ASCII
  hex digits, an abbreviation 4 to 64) for the push, the local merge and `record_review`; `RemoteURL`
  holds both readings of a remote URL, the provider's and the push's same-location key. They share a
  home and not a split: the two rules read the edges differently (where a scheme starts, `file:`,
  `team/.git`, leading slashes, percent escapes), so one split for both would change today's results,
  as the review found it did.
- **2e.** The backup is a clone of the primary (`copyfile` with `COPYFILE_CLONE`, then a rename),
  kept only when it holds the bytes the store validated.
  `CanonicalPath` is the one path helper (`Worktree.resolved`, the sandbox's and the Fix clone's real
  path); `FileStamps.Stamp` is the one file stamp, with the change time `DiffStatResolver`'s had.
  Two stamps are the same version when modification time, size and inode agree, as persistence and
  the catalogues compared before; only the untracked-file counter also asks the change time, as it
  did. (A first attempt compared the change time everywhere: the catalogue and store tests that pin
  "rewritten in place with its date kept, the cache still answers" failed, and it was taken back.)
  `BackgroundWork` takes a priority, the checkout poll passes `.utility`, and its comment is the
  written policy for `BackgroundWork`, `SerialThread` and `ThreadWork`. `SerialThread.sync` and its
  unchecked box are gone with their only test, `syncWaitsBehindQueuedWork`; ordering on the thread is
  still checked by `jobsRunOneAtATimeInOrder`. Expiry and backoff in the git caches read the
  monotonic clock (`MonotonicDate`), injected as before so the tests' clocks are unchanged.
