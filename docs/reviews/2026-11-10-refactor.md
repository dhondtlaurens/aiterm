# Refactor round two: evidence

The [plan](../plans/2026-11-10-obsessive-refactor.md) has ten phases. This record holds what each
one measured and proved; it starts with phase 0, the safety net, and grows as phases merge.

## The audit behind the plan

Nine reviewers each read one lane completely on 2026-11-10, read-only: Operator runtime, Operator
tool handlers, Core Operator rules, app shell, views, Core infrastructure, integrations, daemon,
tests and scripts. Six of their claims were re-checked against the source by the planner and held.
Their findings, with file and line evidence, are the plan's phases. Codex challenged the plan in two
rounds; the second found nothing. The audit ran no build and no test: every number below was
measured afterwards.

### Work budgets

A budget is a count of work for a fixed workload, asserted exactly: a later change lowers the number
in the test with it, and none may raise it. Swift counts come from `WorkMeter`, a task-local a test
binds, so suites running side by side count only their own work and the app counts nothing. Daemon
counts come from a counted `registry.all` and a Python audit hook that sees the worker threads.

Daemon, one steady tick (a workspace at rest, read again with nothing changed),
`daemon/tests/test_tick_budgets.py`:

| Workspace | Registry sorts | File opens | Directory listings | Process spawns |
| --- | --- | --- | --- | --- |
| 6 shell tabs | 6 | 0 | 2 | 0 |
| 2 Claude, 2 Codex, 2 shell tabs | 8 | 0 | 2 | 0 |
| 6 Claude, 6 Codex, 6 shell tabs | 12 | 0 | 2 | 0 |
| 2 Claude, 2 Codex, 2 shell tabs, 20 finished test runs in the queue's folder | 8 | 40 | 2 | 0 |

What the numbers say: the registry is sorted once more for each Codex tab that reports its context,
and every retained test-run record costs two opens on every tick, its record and its lock. A tab
running a foreground command that is no agent costs one process-table read per snapshot (five
snapshots, five reads); that one is recorded, and left for a decision of its own.

Swift, `OperatorWorkBudgetTests` and `WorkBudgetTests` (13 tests). The workload is the frozen
broadcast unless said: 4 tasks, 6 extra worker tabs, one working worker. "Let finish" means the work a
step starts was awaited and counted with it.

Two counts are not stable and only their stable part is asserted. Synchronous saves across the
journey are 0 or 1: its one flush writes only when the 200 ms background save has not written that
revision yet. Background saves run on the writer's own thread, debounced by wall time; they are not
counted, and a budget of them would not be deterministic.
Turn reads across the journey were 72 and 76 on two runs, depending on how many reads were still
under way when the next change came.

Fixture timings, debug build, one machine, reported and never asserted (run with `AITERM_MEASURE=1`):

| Measurement | Median |
| --- | --- |
| `StateStore.save` of the frozen state with 500 shelved tasks added (312 KB), 20 saves | 7.27 ms |
| One status build for a broadcast of 20 tasks and 60 sessions, 200 builds | 0.95 ms |

What the numbers change in the plan's priorities:

- **Status building is cheaper than the audit read it.** One build per session event, two per tick,
  three per mutating call, about a millisecond each at 20 tasks. Sharing one snapshot per pass
  (phases 4 and 5) can take a tick from 2 to 1 and a call from 3 to at most 2: worth doing with the
  restructure, not on its own.
- **Unchanged turns are read again on every event.** Nine reads asked for per session event and per
  tick in a broadcast of ten tabs, each a transcript tail read off the main actor. This is the
  largest repeated work found and the first thing phase 5 should lower.
- **Host lookup by git process is per host call, not per pass:** 40 processes for one cold
  `run_status` over 20 tasks (phase 6), and one per task per minute while reviews are watched
  (phase 5).
- **`worktree list` runs five times per Shelve and three per restore** (phases 2 and 7), and the
  branch watch repeats seven git lookups per pass for a message that has not changed (phase 5).
- **The sidebar derives the requests three times per refresh**, four with the board open (phase 4).
- **A synchronous save of a 312 KB workspace takes about 7 ms in a debug build.** That is under half
  a frame, on the main actor, at each of the 44 flush sites. It is the input for the plan's
  measure-then-decide item, not a decision: the cloned backup in phase 2 removes one of the two
  writes either way.

`Budget.settle` waits on the owners' `last…` task handles. Phase 5 replaces those handles with one
settle seam, and moves this helper to it.

A steady tick opens no transcript: the cost of re-reading a whole transcript after a restore, and
of reading a Codex rollout twice, shows only on a first read or a change, which phase 1 measures
with tests of its own.

### Test support

- `Builders.swift` is the one place tests call the initialisers of `Project`, `TaskItem`,
  `SessionInfo`, `OperatedTask` and `OperatorRun`. The four fixture families (`OperatorUIFixtures`,
  `OperatedWorld`, Core's `OperatorFixtures`, `OperatorServiceFixtures`) and the stubs now build
  through it, with their own values unchanged. The 83, 126 and 37 direct initialiser calls in suites
  move as later phases touch those files.
- `ScratchFolder` hands out folders under one folder per test process, removed when the process
  exits, with the folders of dead processes swept at the next start. The temporary directory held
  197,000 leftovers before this; after a full run with it, none of the new roots remained. The
  three creators behind most of the leftovers go through it now (Operator ports, the controller's
  state file, the worktree suite); the other direct uses of the temporary directory move as they
  are touched. The old leftovers are still there: clearing them is the maintainer's call.
- The test support library reaches Core's internal initialisers through `@testable`, which it
  already did in one file while its manifest comment said otherwise; the comment now says what is
  true, and why the app's build never compiles it.

## Phase 9a and 9b: gate speed

Only 9a and 9b are covered here; 9c remains separate. No phase 0 work budget belongs to
this phase, and no budget or ceiling changed. These are measurements, not budgets.

| Measurement, same machine | Before edits | After implementation |
| --- | --- | --- |
| Full gate execution, excluding queue wait | 720 s | 422.866 s |
| App host | 287.856 s, 1,908 tests in 147 suites | 188.170 s, 1,908 tests in 170 suites |
| Serialized controller tail after the last other app suite | 68.915 s | 0 s |
| Core host | 169.714 s, 2,082 tests | 125.944 s, 2,085 tests |
| Actual simultaneous Swift Testing case bodies, documented default bound 4 | 4 | 4 |

The baseline was an explicit full gate on unmodified source; the last implementation gate was
plain `scripts/test.sh`, selecting the full gate because runner scripts changed. The baseline
included a cold 138.24 s build; the final implementation run built in 0.69 s and 0.54 s. Whole-run
speedup cannot be attributed solely to the controller split. The tail is the difference between
reported controller and last other suite completion durations: baseline controller 287.854 s
versus BannerFixTests 218.939 s; final ControllerApplicationTests 177.891 s versus BannerFixTests
188.168 s. Another post-change full-selection run measured 402.909 s and the same zero tail.
The concurrency probe used an external scratch package through `scripts/test.sh swift`: eight
suites with eight parameter cases each counted active bodies around an awaited 250 ms delay.
All 64 case bodies completed before and after, peaking at four (4.181 s / 4.219 s host time).
Queue waits are separate from all execution numbers.

The serialized controller family became 24 owner suites, with only native application checks
serialized. All 293 test methods across the touched controller files survive; no test was deleted.
Git fixtures copy independent refs and objects from one hermetic seed per process, retain explicit
runner setup for fault/count tests, and await main-actor fixture setup off that actor. Four
host-only review tests use a plain folder and an inert origin reply. The test-only NSTask hook
reports process work lacking the blocking trait; `anUnmarkedProcessIsReported` proves the negative
case with one intentional known issue. `copiedRepositoriesOwnTheirRefsAndObjects` damages one
copy's object and proves another copy remains valid; `anExplicitRunnerStillOwnsFixtureSetup`
preserves runner ownership. The stale lookup test `aStaleLookupIsDropped` uses entry/reply latches,
releases the old answer after cancellation, and joins it before asserting. Waker ordering checks
join their coalesce/send tasks instead of fixed sleeps.

No product defect from the plan's defect table was assigned to this slice. During the blocking
placement change, `aTurnStartedDuringTheWorktreeCheckDefersUntilItEnds` first failed its task-removal
expectation: the test awaited a duplicate coalesced close rather than the retry already scheduled
by the session change. Its failing output is quoted in commit `2f5a5bb2`; the test now joins that
retry. Product code is unchanged. No model-facing, wire, saved-state or frozen fixture bytes changed.

The runner owns a separate seven-day history beside the queue activity records, with per-suite
timings, failing test names, duration excluding queue wait, source identity and exit status.
Activity record format and retention stay unchanged. The history guard proves retention, failure
parsing, clean exact-HEAD provenance, rejection of filtered/incomplete/expired passes, revocation
by a later failed full gate, and capture that finishes with the command even when a grandchild
holds stdout open. An actual filtered Swift run also exercised capture and recorded four suite
timings without becoming full-gate proof. Routing covers the helper, guard and release syntax
reader. Release checks the clean exact HEAD before external operations and again before building,
because the existing README redraw can commit a new HEAD. The history helper's acceptance/refusal
CLI and release syntax were tested; `release.sh` was never executed.

Plain precommit gates passed for each implementation commit. The last implementation gate:
daemon 1,521 passed, 1 opt-in skipped (26.13 s); mypy clean over 79 files; ruff clean; UI 93 in
22 suites (5.497 s); app 1,908 in 170 suites with 1 known issue; Core 2,085 in 175 suites with
3 known issues; snapshots 4 in 2 suites (8.341 s). The added known issue is the intentional
unmarked-process negative probe. Final explicit `scripts/test.sh all` on the committed, integrated
result is required at handoff, with its exact commit and results reported there.

Nothing was dropped. Left and not proven: the existing daemon steady-tick listing test reports
3 directory listings against its ceiling of 2 when local and UTC dates differ (00:00–01:00 CET).
`codex_sessions._list_today` lists both dates; `test_a_steady_tick_stays_within_its_work_budget`
assumes one. Four parameter cases failed first during that interval. Per the Operator, phase 1
will pin the test clock; daemon code, test and ceilings are untouched here. Counting gates ran
plain, without a TZ override, only after local and UTC dates agreed. One queued diagnostic run
was cancelled before admission; filtered Swift/script checks continued during the wait. Installed
latency, real accounts/hosts, release execution and publication were not exercised. Bundle checks,
whole-project documentation close-out and adversarial review belong to 9c and were not done here.
