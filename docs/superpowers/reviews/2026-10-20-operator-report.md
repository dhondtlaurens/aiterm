# Task 5 design and verification

## Before implementation: rulings

Review writes: `handle` creates an independent Task for each tool call. Serialize request_review for the complete host sequence using the published repository plus request number (not task identity). A waiter rechecks original ownership/publication and reads fresh peopleReview after acquiring ownership. Recheck cancellation and validity after host writes before recording; merge into current peopleReview so polling updates survive. Release ownership on success/error/cancellation.

Jira: use a versioned label with the entire run UUID and SHA-256 of the exact UTF-8 raw key. The full UUID separates runs with the same old eight-character prefix; hashing preserves key distinctions, bounded length and Jira-safe characters. Internal find keys remain `find/` plus the raw find key; public `find/` and `find_` reservations remain for backward compatibility. Store new pending writes as `jira_create_v2/<raw key>`, distinct from old `jira_create/<raw key>` without changing persisted models. Completed legacy jiraCreated entries still replay by their exact raw key. An outstanding legacy pending write cannot be safely recovered automatically: its lossy label may belong to another raw key, find or run, even when only one search result exists. Refuse that legacy pending key with explicit manual-reconciliation guidance, retain its marker, and do not search/adopt/create. This deliberately sacrifices automatic legacy pending recovery to prevent either silently adopting the wrong ticket or duplicating a possibly landed write. New pending retries search only the new exact label; multiple matches refuse instead of adopting the first.

GitLab: source and target project IDs differing populate existing forkHead using `project <source ID>:<branch>`. Existing picker refusal then covers GitLab forks without a schema or view change. Equal/missing project IDs preserve ordinary behavior.

All regressions use fake host/network boundaries, no live service writes. Public tool result schemas and persisted-state decoding remain unchanged.

Identity refinements before Jira implementation: normalize the raw key to NFC before hashing, because Swift String dictionaries and pending marker membership use canonical Unicode equivalence. The v2 label must use that same equivalence or a composed/decomposed retry could miss its own ticket. Recovery searches every frozen allowed project, not the latest call's requested project: a retry with changed arguments still names the same original key. It may adopt only one match; multiple matches retain the pending marker and refuse. No result permits changing the original key to bypass manual reconciliation.
